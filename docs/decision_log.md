# Open-ST 产品与技术决策记录

本文件按主题保存讨论中形成的结论、理由和边界。它是完整的结构化决策归档，不是逐字聊天转录。

“已确认”表示需求或方向获批，不等于当前版本已实现。历史方案保留当时语境；后续决策覆盖早期取舍，
当前能力以[实现进度](implementation_progress.md)和[0.1.0发行说明](releases/v0.1.0.md)为准。

状态说明：

- 已确认：用户明确同意，后续不能静默变更。
- 暂缓：方向存在，但细节将在实现前继续讨论。
- 未采用：讨论过并明确不进入当前方案。

## D-001：自行开发 Open-ST

状态：已确认

最初需求是寻找类似 Snipaste、支持截图翻译和 OCR 的干净工具。曾讨论 GitHub 上的 ScreenTranslate，但其项目规模/活跃度带来的可信度疑问和较复杂的使用操作没有满足期望。因此决定在工作区建立自己的项目，名称为 Open-ST。

## D-002：无广告、便携、尽量不污染系统

状态：已确认

不使用安装器、系统服务或 AppData。应用从自身目录运行，设置和日志写入旁边的 `data/`。开机启动只使用当前用户级入口，并能由用户立即关闭或清理。

“尽量干净”同时意味着不捆绑广告、不自动更新、不做后台版本检查、不静默安装开发依赖，也不自动保存截图历史。

## D-003：操作方式以 Snipaste 截图流程为参照

状态：已确认

默认按 `Ctrl+Alt+Q` 进入冻结截图状态，支持窗口/控件检测、自由选区、选区调整和就近工具栏。复制、保存、贴图、标注、OCR 与翻译均从这一流程进入。

这里是交互参照，不要求复制 Snipaste 的品牌、代码或每一个非必要功能。

## D-004：采用 C++20 原生 Windows 技术路线

状态：已确认

用户熟悉 C++，只接触过 Qt，并做过用 Qt 替换 MFC 的项目；WPF/.NET 不熟悉。最终选择 Win32 + D3D11/DXGI + Direct2D 1.1 等系统 API，接受较高开发成本来换取更小的框架负担、更直接的系统集成和可控发布体积。

各组件职责和取舍详见 [技术选型与架构说明](technical_architecture.md)。

## D-005：Qt 不作为主框架

状态：未采用

Qt 的 UI 开发效率和成熟度得到认可，但它需要随包分发运行库/插件，而项目没有跨平台目标。用户的体积预期最初是 50 MiB 以下，因此决定用系统自带 API；50 MiB 后来明确为目标而不是硬限制。

## D-006：SDL 不作为主框架

状态：未采用

SDL 能提供窗口、输入和跨平台渲染基础，但不能替代设置控件、托盘、全局快捷键、文件对话框、UI Automation、开机启动等 Windows 桌面集成。采用后仍需大量 Win32，收益不足。

## D-007：D3D11 而非 D3D12

状态：已确认

D3D12 更底层，要求显式管理命令队列、同步、资源状态和描述符。截图编辑器的二维负载不需要这些额外复杂度；D3D11 与 DXGI、Direct2D 1.1 的互操作更直接，性能也足以实现低延迟冻结和 60 FPS 绘制。

## D-008：Direct2D 1.1 不是过时兼容方案

状态：已确认

Win32 负责窗口和系统消息，Direct2D 负责硬件加速二维绘制。Direct2D 1.1 是以设备/设备上下文为核心、能与 D3D11/DXGI 共享表面的架构代际，Windows 10/11 继续支持并扩展它。它适合本项目的位图、几何、遮罩、标注和文字合成。

## D-009：颜色正确优先于高亮视觉效果

状态：已确认

用户指出 Snipaste 的高亮可能让选区饱和度提升，导致观感和实际截图颜色不一致。Open-ST 仍保留全屏变暗、选区正常的效果，但实现必须只在选区外绘制暗层；选区内不能叠加提亮层。所有输出从遮罩出现前捕获的不可变帧裁切，不能重新抓取屏幕。

## D-010：HDR 不以删功能规避

状态：已确认

50 MiB 不是硬限制，不能为了节省体积或开发方便放弃 HDR/颜色正确性。支持时用 FP16/scRGB 中间路径；普通 JPEG/PNG 经过一次显式 HDR 到 SDR 映射输出 SDR/sRGB，首版不输出 HDR 文件。

具体色调映射参数与测试图：暂缓到图形管线设计阶段确认。

## D-011：鼠标指针提供隐藏/冻结两种模式

状态：已确认

默认隐藏。显示模式记录进入截图瞬间的指针图像、热点和位置；选区包含该位置时才输出。不能在选择完成时再读取实时指针，因为那会违背“冻结画面”的语义。

## D-012：工具栏功能范围

状态：已确认

工具栏包含保存、复制、贴图、马赛克、实心矩形、自由画笔、直线、箭头、空心矩形、椭圆、文字、橡皮擦、撤销、重做、颜色、线宽、OCR、文本翻译和图片翻译。实心矩形默认黑色，作为马赛克之外的另一种遮挡方式。

## D-013：默认 JPEG 95，可选 PNG

状态：已确认

默认保存 JPEG，质量为 95；用户可选择 PNG。使用系统保存对话框并记住上次目录。不产生自动历史或临时截图文件。

实现差异：0.1.0 对话框当前初始选择 PNG，JPEG 编码质量固定95；默认格式设置页尚未实现。D-050记录了当前命名及初始格式，不能将本节目标写作当前默认行为。

## D-014：贴图只接受 Open-ST 产生的图像

状态：已确认

贴图是把当前截图/图片翻译结果固定在屏幕上作参考的窗口。讨论并解释了“把剪贴板图片直接贴到屏幕”后，用户明确不要该功能。因此贴图来源不包括剪贴板。

获得焦点的贴图按 `Esc` 关闭；应用退出关闭全部贴图；不跨重启恢复。

## D-015：托盘不使用双击打开设置

状态：已确认

托盘左键截图，右键显示截图/设置/关于/退出。没有双击打开设置的行为。

## D-016：开机自启默认开启但可配置

状态：已确认

首次欢迎窗口明确显示开机自启状态，默认开启。用户可在设置关闭，关闭后立即移除当前用户启动项。

## D-017：单实例行为

状态：已确认

每个 Windows 用户只运行一个实例。第二次普通启动打开现有实例的设置；`--capture` 请求现有实例开始截图。

## D-018：本地 OCR 使用 Tesseract/Leptonica

状态：已确认

OCR 不上传图片。打包 fast/best 两套 `chi_sim`、`eng`、`jpn` 官方模型；默认 fast 混合识别。模型通过固定 URL 与 SHA-256 在构建时获取，不能提交到 Git。

## D-019：文本翻译与图片翻译分开设计

状态：已确认

文本翻译只上传 OCR 文字；供应商包括 Google 网页翻译（默认）、OpenAI 兼容接口、DeepL 和 Microsoft。

图片翻译需要上传图片，首个供应商为百度，通过 `IImageTranslationProvider` 隔离。第一次上传前提示隐私；马赛克和实心遮挡必须扁平化后再上传，禁止上传未遮挡原图。

## D-020：API Key 明文保存

状态：已确认

用户明确不要求本地加密。API Key 明文写入 `data/settings.json`，设置界面必须说明。网络传输遵循供应商规范，默认 HTTPS 且不能关闭证书验证。这里不把“未加密本地存储”误写成“允许明文网络传输”。

## D-021：代理和请求策略

状态：已确认

系统代理为默认选项，也支持直连和自定义 HTTP 代理（包括 `127.0.0.1:7897`）。文本连接超时 10 秒、总超时 30 秒；图片总超时 90 秒。请求可取消，不自动重试可能计费的翻译；百度令牌获取允许重试一次。

## D-022：项目主页按钮不做版本检查

状态：已确认

最初项目仓库地址不确定，讨论过临时填百度官网。最终采用更简单的方式：开发配置中允许 URL 留空，构建时把值编译进应用；按钮保持可点击，空值时显示“项目主页尚未配置”。不设置禁用状态，不做实际联网版本检查。

最终 Git 仓库地址：暂缓，当前为空。

## D-023：Debug/Release 功能一致

状态：已确认

构建类型主要影响优化、诊断日志和版本显示。Debug 显示 Git 短提交号、记录详细诊断；Release 只显示语义化版本、日志更克制。不能让核心产品功能因构建类型不同而缺失。

## D-024：构建脚本保持两个入口

状态：已确认

- `scripts/build.ps1`：只构建产品，永远关闭 `OPEN_ST_BUILD_TESTS`；支持 Debug/Release、终止型 `-Clean`、`-AllowWarnings` 和 Release `-Package`。Debug 保留增量构建树；Release 在临时目录完成编译后，仅保留 EXE、运行时 DLL、资源和许可证到 `build/Release/`，并删除 CMake/Ninja 中间产物。
- `scripts/test.ps1`：独立构建测试并调用 CTest；最多接受“模块名、case 名”两个位置参数，参数为空时运行全量测试。

`build.ps1 -Clean` 只清理对应配置目录并立即返回，不重新构建；Release 清理同时覆盖其临时工作目录。测试全部产物进入 `testing/testoutput/Debug/`。

## D-025：构建与仓库卫生

状态：已确认

Git 跟踪源代码、测试、CMake、清单、脚本、开发配置、文档和许可证；忽略 `build/`、`testing/testoutput/`、`artifacts/`、vcpkg installed tree、模型缓存、程序生成的 `data/`、二进制和 PDB。

“不提交预编译 DLL”不是禁止发布包包含依赖 DLL。构建时可以从固定、可审计的依赖来源复制 DLL 到 `build/` 或 `artifacts/`，但这些产物目录整体不进 Git。禁止手工扔入来源不明二进制。

## D-026：许可证文件进入发布包

状态：已确认

`licenses/` 保存随程序分发的第三方许可证原文，`THIRD_PARTY_NOTICES.txt` 汇总组件、版本、来源、用途和许可证，用来履行 Tesseract/Leptonica 等依赖的分发义务。它们不是运行时功能文件，但属于合规发布物。

## D-027：测试框架选择 GoogleTest

状态：已确认

讨论与其他轻量 C++ 测试框架比较后，因用户更熟悉 GoogleTest，采用 GoogleTest + GoogleMock + CTest。标准测试链接 `gtest_main` 并由 `gtest_discover_tests()` 注册，不自定义 `main()/wmain()`。平台相关集成 case 先检查环境，不满足时明确 `GTEST_SKIP()`；环境满足后的功能失败不得跳过。测试不能访问真实付费 API；网络通过 mock/fake 响应验证。

## D-028：代码风格和警告策略

状态：已确认

- Microsoft/Allman 风格，四空格。
- 类型和函数 `PascalCase`。
- 局部变量和参数 `camelCase`。
- 私有成员尾随下划线。
- 常量全大写下划线。
- namespace `open_st`。
- 文件名 `snake_case.cpp/.h`。
- C++20。
- 项目和测试使用 `/W4`。
- 默认 `/WX`，可由 `build.ps1 -AllowWarnings` 临时关闭，不必手工改 CMake。
- 第三方和 Windows 头文件按外部头处理，不能通过降低项目警告级别来迁就外部警告。

## D-029：版本与工具链

状态：已确认

- 版本 `0.1.0`，语义化版本。
- Visual Studio 2022 17.10+、MSVC v143。
- Windows SDK 10.0.22621+。
- CMake 3.28+。

## D-030：性能指标是验收目标

状态：已确认

- 快捷键到冻结遮罩典型不超过 150 ms。
- 选区和绘制 60 FPS。
- 托盘空闲 CPU 约为零，不轮询桌面。
- fast OCR 典型选区目标不超过 2 秒。
- OCR 模型加载前空闲内存目标不超过 80 MiB。
- 包体积目标小于 50 MiB，但不能借此删功能或降质量。

## D-031：源码模块独立维护

状态：已被 D-036 的依赖树目录规则替代

`src/<module>/` 必须按模块隔离并拥有自己的 `CMakeLists.txt`。公开头位于模块自己的 `include/` 下，可直接放置或按模块需要继续分层；`.cpp` 位于 `source/`，模块内部头和资源位于按需创建的 `private/`。`src/CMakeLists.txt` 只负责 `add_subdirectory()`，不得集中列举模块内部文件。

## D-032：测试与 Mock 镜像源码模块

状态：已被 D-036 的完整相对路径镜像规则替代

测试位于 `testing/test/<module>/`，GoogleMock 替身位于 `testing/mock/<module>/`，两者分别维护模块级 `CMakeLists.txt`。Mock 只能被测试链接，不能进入产品依赖关系。每个 case 必须有中文注释说明实际验证的功能和关键边界。

## D-033：注释和工程文档使用中文

状态：已确认

项目自有注释、脚本说明和工程文档使用中文，API 名称和固定技术术语可保留英文。注释重点解释设计原因、所有权、单位和平台限制，不做无意义的逐行翻译。项目文本统一 UTF-8、CRLF 和文件末尾换行。

## D-034：Ninja 是当前实现状态，不是永久约束

状态：已确认

当前 `build.ps1`、`test.ps1` 和 CMake preset 暂时保留 Visual Studio 随附的 Ninja。此前没有形成“项目必须使用 Ninja”的设计决策，因此文档不得把它描述为永久架构约束。以后切换 generator 时必须同步修改脚本、preset 和文档。

## D-035：日志采用项目自有同步实现

状态：已确认

`common` 模块中的 Logger 不引入第三方库或后台线程，使用进程内互斥量保护同步文件写入。Debug 构建记录 Debug 及以上，Release 记录 Info 及以上；Release 的 Debug 宏在预处理阶段移除调用和参数求值。文件位于 `data/logs/`，文件名包含创建时刻的本地毫秒时间戳；默认 10000 行或 2 MiB 任一条件触发轮换，每次轮换都按当刻生成新的时间戳文件，并跨进程运行只保留最近 3 个项目日志文件。Error/Fatal 立即刷新，其他级别使用文件流缓冲；任何日志失败均不得影响产品主流程。

业务模块的公开依赖限于 `include/log.h` 中的 5 个日志宏和初始化/关闭函数。`Logger`、`LogOptions` 及测试用的目录注入接口属于内部边界，只放在 `private/logger.h`，不通过 CMake 公开头文件集导出。

日志调用点禁止提交截图内容、OCR/翻译正文、API Key、Authorization 请求头和完整响应体，只允许记录流程状态、错误类别及必要的非敏感数值诊断。

每行记录本地日期和毫秒时间。Debug 构建额外记录相对项目根目录的源码路径和行号；Release 不采集或输出源码位置。

## D-036：目录必须表达模块依赖方向

状态：已确认

产品源码采用嵌套依赖树：`Launcher/Application/Graphics/Capture`。上级目录模块可以依赖其子孙目录模块；子模块不得反向依赖祖先模块，也不得跨出自己的子树依赖兄弟模块。桌面捕获接口、`BgraFrame` 和虚拟桌面物理像素几何统一属于 `capture`，不再保留独立 `foundation` 模块。

`common` 是唯一允许跨层依赖的公共例外，当前包含 Logger；它不得依赖 `launcher` 产品树中的任何模块，也不再设置独立 `logging` 目标。每个真实模块继续拥有自己的 `CMakeLists.txt`、`include/`、`source/` 和按需存在的 `private/`。

`testing/test/` 与 `testing/mock/` 必须完整镜像源码相对路径，分别形成 `Common` 与 `Launcher/Application/Graphics/Capture` 两棵入口。测试名称前缀按实际目标模块使用 `common`、`launcher` 或 `capture`。

## D-037：用户可见文本统一通过本地化模块取得

状态：已确认

本地化资源使用文本键优先的 JSON 结构，不跟随系统语言，无设置时默认 `en-US`。语言代码由各文本对象的属性名动态提供，设置窗口直接显示代码，不增加语言元数据或 C++ 语言清单。允许新增语言缺少部分译文；查询缺少当前语言时回退同一 key 的 `en-US`，仍缺少则显示固定 `?` 并记录诊断。

业务代码只允许通过 `GetUiText("text.key", ...)` 取得用户可见文本，范围包括托盘、菜单、窗口标题、普通提示和错误弹窗。调用处直接指定 JSON key，不在 C++ 中维护枚举、索引数组或第二份 key 注册表。只有资源加载失败时的最小三语紧急提示例外。

资源只在实际读取请求发生时检查文件版本和重新加载，不使用目录监听线程，不要求静止界面主动刷新。JSON 语法或固定外层协议无效时，本地化继续使用已生效业务文本；按 D-045，Common 的本次读取失败不会被旧缓存伪装成成功。确定无效的同一文件签名不重复解析，签名变化后重试。

nlohmann/json 因此成为基础依赖；`resources/ui_text.json`、`resources/default_settings.json`、第三方通知和 nlohmann/json 许可证必须随发布包一起分发。

## D-038：通用 JSON 单例、设置存储与第一阶段设置窗口

状态：历史决策；公开接口和设置归属已由 D-045 修订，单例、缓存与安全写入能力保留。

`common` 提供进程内唯一的 `JsonFileManager`。各模块用动态卡名和路径取得 `JsonFileHandle`；管理器强持有名称绑定和内存快照，取句柄不读盘，每次实际读写先检查文件版本。Common 不维护业务卡名、路径、设置 key 或本地化 key 清单。读取返回不可变快照；创建只允许目标缺失；更新使用同目录临时文件、提交前冲突检查和原子替换。

## D-042：原生冻结帧与覆盖预览分离

状态：已确认

历史取舍（模块拆分部分已由 D-048 替代）：当时 HDR 适配不新建独立 CMake 模块或子模块，而是在既有依赖树内按职责拆文件：`OpenST::Capture` 负责 `FrozenDesktopFrame`、逐输出原生 plane、DXGI 格式协商和 CPU 自有像素；父级 `OpenST::Graphics` 负责从该模型生成呈现缓冲（当前按 D-043 逐屏选择 BGRA8 或 FP16）；`OpenST::Application` 只协调会话所有权和上传时序。这样保持 `Launcher/Application/Graphics/Capture` 的单向依赖，不产生 capture 反向依赖 graphics，也避免一个只被单一父模块使用、却带来额外 public API 和链接边界的微型目标。

最初的 BGRA8 全桌面预览已被 D-043 的逐屏原生呈现取代，原生冻结位深仍不被覆盖。后续选区裁切、剪贴板、JPEG/PNG、OCR 和翻译只能消费 `FrozenDesktopFrame`，不能消费覆盖预览；导出用 HDR→SDR 参数和基准图当时留在输出阶段单独审核，产品接入结果见 D-048。

实验只修改 CaptureSingleOutput：取消 LastPresentTime 非零过滤及三次重试，直接使用 AcquireNextFrame
成功返回的资源；保留单次500ms等待、HRESULT检查及Acquire/Release和Map/Unmap资源管理。用户自行构建
Debug并验证，反馈“直接黑屏了”。这次结果来自用户观察，未采集返回纹理像素、逐屏元数据或独立截图证据。

结论：本机当前捕获路径不能以“取消过滤、直接接受首次成功返回”作为该问题的修复；用户要求后已完整恢复
实验前的 LastPresentTime 过滤和最多三次尝试。该观察支持继续保留首帧保护，但不能推导所有DXGI仅鼠标
更新返回的图像都无效，也尚未定位黑屏具体发生在返回纹理、复制还是后续呈现阶段。

截至本次回滚时，快速移动鼠标导致三次机会提前耗尽的缺陷仍未修复。500ms总等待预算尚未实施，也未
经本次实验验证；后续需同时验证持续鼠标移动、静止桌面及首帧内容，不能通过接受黑图或隐藏错误判定成功。
本次回滚未重建可执行文件；用户之前构建的实验Debug产物需重新构建才会恢复原行为。

### 后续实验：每个显示输出共用 500 ms 等待预算

2026-09-08 用户批准改为总等待预算后复测。CaptureSingleOutput 使用 steady_clock 在每个输出开始获取帧前
建立一次 500 ms 截止时间；仅鼠标更新帧仍释放并跳过，后续 AcquireNextFrame 只使用剩余时间，取消三次限制。
剩余时间向上取整到毫秒，系统调度和接口返回可能使实际耗时略超预算；该预算不包含初始化和纹理读取，
也不是整个多显示器截图共用 500 ms。真正的接口错误仍立即失败，超时诊断包含显示输出及跳过的鼠标帧数。

2026-09-08 用户复测后反馈“看起来没问题”，接受当前总等待预算机制；此为本机手工复测结果。

## D-053：Settings JSON 窗口与按控件 ID 绑定

## D-054：通用 Renderer 迁移及错误/关于窗口复用
