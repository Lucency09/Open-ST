# HDR 跨屏交互掉帧诊断与优化方案

日期：2026-09-14。状态：用户已授权自行安排诊断测试；诊断已完成，生产优化未实施。
结果见 [诊断报告](../cross-screen-frame-pacing-report-2026-09-14.md)，具体生产整改见
[统一重绘方案](cross-screen-redraw-v0.3.md)。下文保留诊断前的计划，实际执行范围与限制以报告为准。

## 1. 目标与已知事实

用户将跨屏掉帧列为下一步优先事项，UI Automation 子控件识别降为低优先级。
本方案聚焦冻结遮罩出现后的选区创建、移动、缩放和跨屏交互，沿用交互 60 FPS 目标。
快捷键到遮罩出现的 150 ms 启动目标单独记录，不混入本轮交互指标。

当前源码链路：

- `app.cpp` 的 `WM_MOUSEMOVE` 更新选区或窗口候选后调用 `CaptureOverlaySession::Invalidate`。
- `capture_overlay_session.cpp` 对全部屏幕调用整窗 `InvalidateRect`；这只是请求重绘，不代表每条鼠标消息都实际绘制。
- 各屏 `WM_PAINT` 在同一 UI 线程分别取 `SelectionForDrawing` 快照并调用 `OverlayRenderer::Render`。
- `overlay_renderer.cpp` 每次绘制检查 DXGI 工厂和参考白状态，整屏绘制冻结图、暗层、边框与控制点，然后 `EndDraw`、`Present(1, 0)`。
- 参考白验证在有对应元数据时经 `DisplayConfigGetDeviceInfo` 查询系统。

待验证假设是呈现等待、系统状态查询、全屏绘制负载或消息调度导致卡顿。
以上代码事实不能证明根因，更不能直接推导多屏耗时等于屏幕数乘刷新周期。

## 2. 阶段 A：先建立可比较的诊断基线

本次建议仅批准阶段 A；得到结果后提交阶段 B 的具体修复设计，另行审核。

### 采样设计

- 显式诊断开关默认关闭，不增加用户设置页；关闭时不分配采样缓存、不计时、不持续轮询。
- App 拥有单次截图会话的统计；Graphics 只提供自身绘制分段的可选测量结果，不依赖 App 或 Settings。
- 用单调高精度时钟记录输入处理、失效请求、开始绘制、颜色校验、D2D 命令记录、EndDraw 与 Present 的 CPU 时间。
- 每次可见状态变化关联递增修订号；每屏记录绘制使用的修订号，区分请求合并、旧状态跳过及各屏提交差异。
  合并后按实际绘制修订及其首次请求时间计算延迟，已跳过修订单独计数，不将其等待时间算到最终帧。
- 输入到绘制延迟定义为应用处理可见状态变化到对应绘制开始；不是物理鼠标到显示器发光延迟。
  Win32 消息时间仅作辅助粗粒度队列延迟指标，不直接与高精度时钟相减；当前 GetCursorPos 取最新位置的行为保持不变。
- 有界预分配缓存，例如最多 16384 条记录，溢出记录计数；最多保留一个待汇总会话，不无界增长。
  热路径不逐帧写文件、不记录图像、窗口标题或正文。会话结束后再汇总；丢失样本的运行不能冒充完整基线。
- 输出每屏分段 P50/P95/P99、长间隔比例、输入更新数、重绘请求数、实际绘制及提交次数。
  长间隔只统计持续可见变化的活跃区间，排除静止、模态和会话收尾；有效样本数随结果报告。
  EndDraw 的 CPU 时间不等于 GPU 完成耗时；Present 返回间隔不等于真实显示帧率。
- 若 CPU 分段不能解释问题，补充可用的系统 ETW/DXGI 呈现跟踪；明确工具及指标定义、采样开销和追踪是否成功。
  无实际显示证据时只报告提交节奏，保留实际 FPS 与视觉验收未完成状态。

### 场景与方法

先记录本机显示器数量、分辨率、刷新率、缩放、HDR 状态、适配器及构建版本，不引用旧报告当作当前配置。
用户已确认掉帧最明显出现在拖动或缩放跨屏选区，首轮优先复现已有跨屏选区的移动与缩放，创建作为对照。

每种可用场景预热后运行至少三次，每次约 15 秒持续操作，静止状态另测：

1. 同一多屏配置内分别在 SDR 屏、HDR 屏操作，然后跨屏来回操作。
2. 自由框选、已有选区移动、八控制点缩放，以及窗口预选切换分别统计。
3. 当前混合刷新率/DPI 为主场景；单屏、纯 SDR 等对照仅在实际条件具备时执行。
   不自动更改系统 HDR、刷新率或显示布局；未执行的组合明确标记。
4. 显式区分首次截图与稳定交互、诊断开关开/关的扰动，不用 Debug 耗时作产品性能结论。

Release 用于性能采样，Debug 用于正确性验证。阶段 A 的交付是可复现步骤、分段数据、瓶颈判断及证据不足项，
不是承诺已经达到 60 FPS。如果无法复现，报告场景覆盖和缺失条件，不强行选择优化。

### 范围和验证

预期涉及 Application 的会话统计私有类型、`app.cpp` 输入/绘制/收尾接入，Graphics 的
`overlay_renderer.h/.cpp` 可选测量接口，以及相应镜像测试和模块 CMake 清单。
只有统计生命周期确需时才调整 `capture_overlay_session.*`；最终新增文件清单在施工前核对。
保持 Present 参数、颜色验证频率、图像格式、单线程资源所有权和取帧算法不变。

测试覆盖：默认关闭、容量溢出、分位统计边界、会话重建清空、取消/失捕/失败收尾及过期修订不归入新会话。
继续运行受影响 Application/Graphics 测试、Debug /W4 /WX 和 Release 构建；复用现有像素测试检查原生 SDR/FP16 行为。
既有 PinWindow 失败独立记录，不为诊断全绿修改无关模块。检查 git diff 和产物目录。

## 3. 阶段 B：按证据选择单项修复，另行审核

| 证据 | 候选方向 | 必须保留的约束 |
| --- | --- | --- |
| Present 等待主导、消息处理受阻 | 统一最新快照的重绘调度，评估可等待交换链与消息感知等待 | 不在 UI 线程无条件阻塞等待；静止无忙循环；每屏进度、取消与句柄生命周期正确 |
| 多屏重复绘制或 GPU 负载主导 | 按屏幕可见结果变化减少重绘，必要时再评估局部更新 | 同时处理新旧暗层、边框及控制点；跨屏拼缝不画伪边框；窗口暴露时能强制恢复 |
| 参考白或工厂校验主导 | 设计会话级校验与失效机制 | 不直接删除校验；无通知情况下的颜色变化检测时限属于行为变化，须明确审核 |
| 消息/候选计算主导 | 按实测热点调整输入与绘制协调 | 不丢弃按下/抬起/取消语义，不把候选当正式选区 |

不预先无条件改成 Present(0)，不将多线程渲染、设备复用、HDR 算法、贴图层级优化或 UIA 纳入本轮施工。
若证据要求扩大范围，先说明差异并重新审核。

## 4. 修复验收原则

- 相同机器、显示配置、操作与构建模式做前后对照；报告分位数和长帧比例，避免只看平均值。
- 60 Hz 及以上输出以 60 FPS 为目标，报告超过 16.67 ms 和 33.33 ms 的有效更新间隔比例；
  低刷新率输出受物理刷新率限制，不能套用同一达标判据。精确容差在基线后确定并随修复方案审核。
- 创建/移动/缩放、跨缝、候选确认、取消、失捕、保存取消恢复、显示变化取消会话均保持正确。
- HDR 原生亮度精度、SDR 输出、无伪边框、静止低 CPU 及关闭后的资源释放不能退化。
- 实际跨屏观感仍需用户确认；自动测试或 Present 次数不能代替视觉验收。
