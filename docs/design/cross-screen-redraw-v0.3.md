# 跨屏选区统一重绘整改方案

日期：2026-09-14。审核更新：2026-09-15 用户批准按本方案施工，实施与验证结果见进度表。
实施更新：已完成生产实现与自动验证，用户于 2026-09-15 确认原跨屏掉帧解决，见 [整改收尾](../cross-screen-redraw-implementation-2026-09-15.md)。
依据：[诊断报告](../cross-screen-frame-pacing-report-2026-09-14.md)。

## 1. 本次要解决的问题

每屏独立等待 `WM_PAINT` 时，持续输入与逐屏 Present 等待会造成绘制机会分配失衡。
本机在副屏捕获期间把选区移到主屏，可观察到主屏约 20–32 次/秒的提交；
仅统一重绘批次的实验恢复到约 60 次/秒，且松开／重按不再改变每屏获得绘制机会的数量。

本次目标是让一次选区更新在一个会话批次内公平送达所有需要重绘的输出。
保留鼠标捕获在按下窗口、抬起释放的语义，不以跨屏切换捕获来绕过渲染问题。
不承诺本阶段完成全部 HDR 性能目标；144 Hz 独立更新、约 33 ms 尾延迟和高 CPU 继续另列。

## 2. 具体行为

### 输入与批次

1. 输入继续由原 App 选区状态机处理；原有 `Invalidate()` 合并窗口失效请求。
2. 任一遮罩收到有效绘制请求时，进入 App 的统一重绘入口，而不是只绘制消息所属屏幕。
3. 入口一次读取 `SelectionForDrawing()`。候选预选、正式选区、暗层、边框和控制点均使用同一份快照。
4. 在调用任何 renderer 之前固定本批待绘制输出并处理它们已有的无效区域。
   随后按会话输出顺序，每个输出最多绘制一次；不让下一屏继续等待另一条 `WM_PAINT`。
5. 输入变化仍按现状使全部输出失效。窗口暴露、恢复或系统独立失效必须触发实际重绘，
   不得因为选区修订没变而跳过系统要求的恢复绘制。
6. 批次结束后只有存在新请求才安排下一批；静止状态没有定时器、轮询或主动连续呈现。

这里的统一批次保证每屏有执行机会，不代表两个物理显示器原子同步显示。

### 新请求、重入与关闭

- 会话保存单调请求代次和批次状态。开始批次时记录代次；批次期间的新失效保留到下一批，
  不能在最后一次 `ValidateRect` 或状态清零时被吞掉。
- 所有本批无效区域在开始绘制前处理；不得先绘制第一屏、再清空第二屏期间新收到的请求。
- 重入的绘制消息只记录待重绘，不嵌套启动第二轮渲染。退出外层批次后统一补发必要请求。
- App 标识正在渲染的状态。显示配置变化、窗口销毁、取消或退出若在图形调用中重入，
  先记录关闭／失效请求，阻止继续访问失效输出；在外层调用安全返回后释放 session、renderer 和冻结帧。
- 窗口已销毁的记录立即失去可用 HWND；关闭依然先解绑回调，再销毁资源。
  不在等待期间保留可跨新会话使用的裸窗口消息或旧对象指针。
- 任一屏渲染失败停止该批，沿用现有统一取消和本地化错误提示。
  模态完成忙状态下沿用延迟清理／提示语义，不重复弹窗，也不保留半有效截图会话。
- 保存取消后恢复、首次显示及强制重绘进入同一协调入口；原来隐藏阶段准备首帧的顺序保持不变。

## 3. 改动范围

| 文件范围 | 目的 |
| --- | --- |
| `Application/include/app.h` | 声明私有重绘入口及必要的渲染／延迟关闭状态 |
| `Application/source/app.cpp` | 接入 WM_PAINT、重入通知和统一清理保护 |
| `Application/private/capture_overlay_session.h` 与对应 `.cpp` | 封装输出遍历、请求代次和批次资源边界，不对外泄漏可长期持有的输出容器 |
| 可选 `Application/source/app_overlay_render.cpp` | 若入口逻辑较长，在同模块拆分实现，避免继续堆积 app.cpp |
| 镜像 Application 测试及该模块 CMake | 加入批次调度与生命周期回归；只有新增文件时更新源码清单 |
| 进度表、开发规范和决策记录 | 在方案批准与实施后同步实际契约及验证结果 |

保持 Graphics/OverlayRenderer 的 Present 参数、颜色校验、FP16/SDR 像素链路和设备创建不变。
Capture 取帧、HDR 映射、PinWindow、导出、快捷键设置与 UI Automation 不在本轮改动范围。
不把测试目录中的硬编码两屏数组、模拟轨迹或诊断标志带入产品；实现必须适用于实际输出数量。

## 4. 分步施工与验证

### 第一步：请求和生命周期边界

实现私有的批次准入、请求代次、重入和延迟关闭逻辑，先用可控 renderer 边界验证：

- 多次失效只形成一个待处理批次；同一快照覆盖每个待绘制输出且每屏最多一次。
- 渲染期间追加失效不会丢失；没有新请求时不自发重复绘制。
- 三个以上输出、不同消息接收屏及不同输出顺序均不遗漏输出。
- 渲染重入、第二屏失败、显示变更／销毁／退出请求均不释放仍在使用的资源。

### 第二步：接入真实窗口绘制

接通真实 `WM_PAINT`、系统暴露重绘与已有取消／模态恢复路径。
验证旧边框、控制点和暗层被正确擦除，跨缝不出现伪边框；不引入局部裁剪优化。
重新执行窗口预选确认、创建／移动／缩放、失捕、Esc、保存取消恢复的相关 App 测试。
复用 Graphics 的 SDR／FP16 像素回读测试确认输出未退化。

### 第三步：原生手势对照与收尾

- Debug `/W4 /WX`、Release 构建通过。
- 运行受影响 Application、Graphics、Selection 回归；根据实际改动再决定是否需要全量。
  原有无关 PinWindow 已知失败单独报告，不降低断言。
- 复跑报告中的两个起点、四阶段真实按钮／鼠标路由，每组至少三轮，并核验前台、捕获、清理和原始记录完整性。
- 在本机受控场景检查两屏每批次数对应，原受影响主屏阶段恢复到约 60 次/秒，
  不再出现原先约 100 ms 级的持续无绘制机会；报告 P95、最长及阶段头尾间隙。
  数值只用于本机前后对照，不写进机器无关 CI 的硬阈值，也不改称实际显示 FPS。
- 实际产品再由用户复核其原始跨屏拖动／松开重按操作；未完成视觉复核时明确保留。
- 检查 git diff、源码／测试目录和构建产物，更新文档，子 Agent 监督变动及最终复核。

如果统一批次不能在产品路径改善原问题，或者必须改变 Present、渲染线程、颜色验证等范围，
暂停扩展并提交新证据和修订方案。本次批准不自动授权这些后续优化。
