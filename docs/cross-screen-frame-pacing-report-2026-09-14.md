# 跨屏拖动掉帧诊断报告

日期：2026-09-14。版本：0.3.0。状态：诊断完成，生产修复待审核。
后续更新：2026-09-15 用户批准后已完成统一重绘实现，见 [整改收尾](cross-screen-redraw-implementation-2026-09-15.md)。
本文保留整改前诊断数据及假说核对，不以新结果改写历史记录。

## 1. 结论

本机已复现与鼠标捕获归属相关的重绘机会分配失衡：**在 SDR 副屏按下并保持捕获，
把选区拖向 HDR 主屏时，主屏收到的实际绘制／呈现提交明显减少；在主屏松开重按后恢复。**

原实现让每个遮罩窗口独立等待 `WM_PAINT`，并在同一 UI 线程分别绘制、调用 `Present(1, 0)`。
持续鼠标输入与较慢输出的呈现等待叠加时，主屏可以长时间得不到绘制机会。
仅在独立探针中把重绘改成统一批次，保持颜色处理和 Present 参数不变，就能稳定消除本轮观察到的两屏提交数失衡。
这支持首先整改 Application 的会话重绘编排；不需要先修改 HDR 算法、鼠标捕获归属或交换链参数。

这里定位的是已复现的故障机制，不把 Windows 内部如何选择下一条绘制消息描述为已证明的固定规则。
用户描述的另一方向，本次没有复现同等程度的失衡；不能声称双向所有现象都已得到完全解释。

## 3. 方法与证据等级

用户授权自行决定诊断测试，生产整改仍需另行审核。
测试程序和生成的计时源码副本全部放在 `testing/testoutput/Debug/benchmark-release/frame-probe/`，
没有修改生产源码、产品 CMake 或正式测试用例。正常产品不包含诊断分支。

### 探索阶段

完成 18 组普通定时器对照：移动／缩放、双输出／仅主屏输出／仅副屏输出，各三轮，每组 15 秒。
这些单输出对照仅减少探针创建的遮罩窗口，不是禁用系统显示器。
确认较长 CPU 墙钟等待集中在 Present，颜色查询和 D2D 命令记录／EndDraw 很短。

高频 posted 消息压力探针进一步观察到绘制失衡，但它与系统合并的鼠标消息优先级不同；
早期未成功激活前台的探针也存在环境差异。因此这些结果仅用于发现方向，**最终结论使用下面的原生手势对照**。
探索中 Present(0) 和 DO_NOT_WAIT 没有显著消除慢屏等待，不将其写成有效修复。

### 正式原生手势对照

共 12 组有效运行：两个起点屏幕 × 原实现／集中重绘实验 × 三轮，每组 16 秒，四阶段各约 4 秒。

1. 在起点屏幕内部按下已有选区并移动。
2. 不松开，移到另一屏幕并继续在该屏内部移动。
3. 在目的屏释放左键，再按下同一选区并在该屏内部移动。
4. 不松开，移回原屏并继续移动。

选区为 400×240 物理像素，内部起点距拼缝 600 像素；两次转场前约 1 秒平滑跨屏，其余时间局部移动。
已有选区由模型准备，未重测截图创建过程或快捷键启动耗时。

按钮使用 `SendInput`；独立高分辨率定时器线程约每 8 ms 调用 `SetCursorPos`，
由 Windows 自然生成、合并和路由鼠标移动消息，不向 App 伪造移动消息。
App 原有按下、移动、抬起和 `SetCapture/ReleaseCapture` 路径实际执行。
主线程使用 `GetMessage`；低频控制消息只负责阶段切换和终止，不产生选区输入。
此方式覆盖原生窗口消息路由，仍不等同于某款实体鼠标的 USB/HID 输入时序。

每次按下、阶段切换及完成都核验捕获／焦点／前台 HWND；每条输入记录核对接收窗口与捕获 owner。
12 组全部通过：前台和捕获归属正确、无指针设置失败、无图形错误或记录溢出、左键释放、捕获清空、原指针位置恢复。

### 单变量实验

集中重绘实验只改独立探针中的 `WM_PAINT` 编排：一次取选区快照、清除本批两窗失效区域、依次绘制两屏。
Present 仍为 `(1, 0)`，颜色校验、原始像素、绘制算法、设备创建和输入轨迹保持相同。
此实验用于因果验证；它尚未具备生产实现需要的完整重入和新请求保护，不能直接复制交付。

## 4. 三轮结果

下表是**呈现成功返回的更新提交率**，不是显示器真实显示 FPS。每个阶段含跨屏过程，时长由阶段标记实际计算。

| 操作与观察输出 | 原实现提交率（三轮范围） | 集中重绘提交率 | 原 P95 提交间隔 | 集中重绘 P95 |
| --- | ---: | ---: | ---: | ---: |
| 副屏起拖，不松开移到主屏：观察主屏 | 20.01–24.56 次/秒 | 60.04–60.11 次/秒 | 116.50–133.10 ms | 33.30–33.33 ms |
| 主屏起拖，副屏松开重按，再拖回主屏：观察主屏 | 19.69–32.25 次/秒 | 59.81–60.05 次/秒 | 83.58–133.14 ms | 33.06–33.33 ms |
| 到主屏后松开重按，只在主屏移动：观察主屏 | 59.59–60.34 次/秒 | 59.84–60.08 次/秒 | 33.22–33.29 ms | 33.21–33.26 ms |
| 到副屏后松开重按，只在副屏移动：观察副屏 | 59.76–59.93 次/秒 | 60.19–60.58 次/秒 | 32.89–33.01 ms | 33.22–33.23 ms |

例如副屏起拖到主屏这一阶段，原主屏三轮分别提交 96、80、99 次，实验分别提交 242、241、245 次。
原实现该阶段最长相邻提交间隔约 134 ms；另一回到主屏的阶段，末尾还观察到约 116 ms 无新提交。
分析同时保留阶段首尾空白，未用“超过某个阈值就删掉样本”的方式隐藏长停顿。

原实现中，捕获仍在副屏但选区也在副屏时，主屏绘制不足可能并不显眼，因为主屏只显示不变暗层；
按住移回主屏后，同样的绘制不足才直接影响正在移动的选区。这与用户反馈的松开／重按关联相吻合。

颜色校验的分阶段 P95 最高约 **0.014 ms**；D2D 命令记录加 EndDraw 的 P95 最高约 **0.258 ms**。
这些 CPU 分段不足以解释百毫秒级更新空白。EndDraw 的 CPU 时间不等于 GPU 执行时间，未据此排除所有 GPU 或驱动因素。

## 5. 未解决与未验收

- 集中重绘后仍约 60 次/秒，P95 间隔仍约 33 ms，尚未实现主屏 144 Hz 独立更新或严格均匀的 60 FPS。
- 探针活动期进程 CPU 为原实现约 86–91%、实验约 88–92% 的**一个逻辑核**；此项未改善。
  这是包含驱动及测试线程的进程读数，不是系统总 CPU 百分比，也未归因到某条 CPU 指令。
- 统计插桩开销未单独量化；A/B 使用相同插桩。原生手势探针的绝对耗时不作为物理输入到显示延迟验收。
- 没有使用 ETW／显示帧统计证明实际显示 FPS，也没有完成连续画面的肉眼流畅度验收。
- 相反方向未出现同等程度饥饿；其他刷新率、DPI、驱动和 Windows 10 环境未覆盖。
- 保存模态、显示器移除、设备失效和生产批次重入属于整改后的回归范围，本轮不宣称已验收。

## 8. 2026-09-15 补充：焦点窗口是否获得更多绘制机会

### 猜测来源与落档级别

用户提出：在屏幕 A 按下左键并拖到 B 后，焦点仍属于 A 的遮罩窗口；
因此怀疑系统给焦点所在窗口更多 `WM_PAINT` 处理机会，导致后来到达的屏幕更新不足。
这里的“焦点”应指窗口 HWND 的键盘焦点，不能把屏幕、键盘焦点、前台窗口和鼠标捕获混为同一个概念。

**落档级别：有场景相关性支持、尚未因果隔离的猜测；概率未定，不标“大概率”或“已论证”。**
本次核对既有源码、原始测试记录和微软公开文档，并由子 Agent 独立复核；没有新增焦点隔离实验。
没有找到直接支持该窗口优先级规则的公开依据，不等于证明系统内部绝不存在类似行为。

### 已证实内容与未证实内容

| 命题 | 证据与状态 |
| --- | --- |
| 本项目在 A 按下后，跨屏移动不会主动把焦点／捕获切换到 B | 已核对源码：`app.cpp:1476–1477` 按下时调用 SetFocus／SetCapture；移动分支不切换，抬起在第 1517 行释放捕获。正式手势日志也确认按住期间归属不变。仅松开不构成本程序显式切换焦点，B 上重按才设置 B |
| 绘制失衡与焦点／前台／捕获的共同归属有关 | 本机重复观察到相关性：三者共同属于 SDR 副屏时，HDR 主屏更新明显减少；改在 HDR 主屏按下后恢复。统计和方向限制见第 4 节 |
| 键盘焦点本身让系统更优先派发该窗口的 WM_PAINT | 未验证：现有测试没有仅改变键盘焦点、固定其他因素，因此不能从相关性推出这一因果规则 |
| 焦点窗口必然比同线程其他窗口获得更多绘制机会 | 现有样本不支持这种概括：`native-origin0-r1` 阶段 0 焦点在 HDR，但两屏各 243 次提交；`native-origin1-r1` 阶段 2 两屏各 238 次。这不排除有条件的影响，但限制了“焦点必然优先”的说法 |
| 统一批次重绘能改善本轮复现的失衡 | 单变量 A/B 已支持，见第 3–4 节；隔离的变量是重绘编排，不是焦点。整改有效不能反推焦点假说成立 |

上述提交计数是成功 Present 返回的统计，不是对系统 WM_PAINT 内部生成数量或内部优先级的直接测量。

### 为什么还没有完整论证

1. 正式按下操作同时改变 `GetFocus`、`GetForegroundWindow`、`GetCapture` 和鼠标消息接收 HWND，
   缺少焦点独立变化的对照。窗口激活还可能改变 Z 序，这个因素也未单独记录和控制。
2. 两屏同时具有 144／60 Hz、HDR／SDR、100%／150% 缩放差异，Present 等待也明显不同。
   现有实验没有将这些因素与窗口状态变化完全分离。
3. [GetMessage 文档](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getmessagew)
   规定默认消息类别顺序，输入先于普通 WM_PAINT；该说明未给出“同线程焦点窗口的 WM_PAINT 优先”保证。
4. [SetFocus 文档](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setfocus)
   描述键盘焦点，并说明该调用还会激活目标窗口或其父窗口，因此直接调用 SetFocus 不保证只改变焦点。
   [SetCapture 文档](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setcapture)
   描述鼠标输入路由。这两种职责本身不构成绘制优先级证明。
5. [Window Features 文档](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features)
   提到前台线程通常获得较多 CPU 时间。但我们的两个遮罩属于同一 UI 线程，
   不能据此推导同线程两个窗口之间的绘制次数如何分配；该文档描述的激活与 Z 序关系也未证明焦点因果。

### 若后续需要提高证据等级

先验证能够独立控制并持续记录焦点、前台、捕获和输入接收窗口；如果改变焦点导致其他状态一起改变，
该组不能冒充焦点单变量实验。再固定输入轨迹、失效请求、输出配置、窗口顺序与呈现方式，
对比仅改变焦点的情形，并分别检查前台／捕获／Z 序因素。
计时点应覆盖 GetMessage 返回、WM_PAINT 入口、绘制与 Present，避免把呈现等待误判为消息生成优先级。
即使本机因果对照成立，结论也先限定到已测配置；上升为 Windows 普遍规则仍需更广验证或明确的机制依据。

这是假说的后续验证条件，不表示这些实验已经执行，也不改变现有统一重绘方案的待审核状态。
